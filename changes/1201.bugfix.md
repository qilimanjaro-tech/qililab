Fixed incorrect Q1ASM emission on Qblox buses when a `wait` or `wait_trigger` immediately followed a pending parameter update (e.g. `set_frequency`, `set_phase`, `set_gain`). The compiler previously always split the flush into a separate `upd_param 4` instruction plus a following `wait`/`wait_trigger`, which undercounted the tracked duration for waits longer than the Q1ASM max, and — since `wait_trigger` no longer relies on an unconditional `wait_sync` to force buses back in sync regardless (see the following changelog entry) — left a bus with a pending update watching the trigger network for less time than the others, e.g. only 96 ns of a requested 100 ns `wait_trigger`, desynchronizing it from the rest.

`QbloxCompiler._handle_add_waits` now merges the pending update into the wait itself when it fits in one instruction, and tracks the actual emitted duration for long waits — handled by `qpysequence`'s `upd_param` flag on `LongWait`, instead of being computed manually in `QbloxCompiler`. `QbloxCompiler._handle_wait_trigger` instead flushes the pending update on every affected bus with its own separate `upd_param` instruction *before* the buses sync on the trigger, so every bus still waits the exact same requested duration once the trigger arrives.

Concretely, the generated Q1ASM changes shape: where a pending parameter update before a `wait` used to always show up as `upd_param 4` followed by a separate `wait <duration>`, it now shows up as a single `upd_param <duration>` line when the combined duration fits in one instruction.
